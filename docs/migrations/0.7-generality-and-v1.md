# 0.7.0 — general vocabulary + A2UI v1.0 conformance

_Status: **planned, not yet shipped.** Published today: 0.6.0. This document exists so
consumers can object before it lands, not after._

Two things happen in 0.7.0, and it matters that they are separate:

|                           | what changes                               | who does work             |
| ------------------------- | ------------------------------------------ | ------------------------- |
| **A2UI v1.0 conformance** | the shape of the `catalog.json` _document_ | nobody                    |
| **De-domaining `intel`**  | the InsightCard _vocabulary_               | intel consumers, one edit |

## 1. v1.0 conformance changes the schema, not the wire

Our contracts were authored before the v1.0 catalog schema rules were final. They use custom
`$defs`, `allOf` + `componentCommon` wrappers, and local copies of protocol primitives — all three
of which v1.0 either prohibits or supersedes. 0.7.0 compiles each contract into a conformant
document: helpers inlined, protocol primitives `$ref`'d to the spec's own `common_types.json`, the
`ComponentCommon` wrapper dropped because the envelope composes it.

**No component gains, loses, or renames a property.** A stream that validated against 0.6.0
validates against 0.7.0 unchanged. So:

- **`ops` and `forms` keep their existing catalog ids.** The id names the vocabulary, and the
  vocabulary is byte-identical. Re-encoding the schema is not a breaking change, and minting a new
  id for it would be a lie about what changed.
- **No action for ops or forms consumers.** Not a re-gate, not a prompt-pack pull, nothing.

If you validate emissions against the contract document yourself, note that it now `$ref`s
`https://a2ui.org/specification/v1_0/common_types.json` — your validator needs that schema
registered. Ours vendors it (`@aurilabs/core/a2ui-common-types.json`) so validation stays offline
and deterministic; you're welcome to the same copy.

## 2. `intel` becomes `insight`, and stops naming anyone's business

This one is a real change, and it is our mistake to fix.

`intel` shipped two enums that encode a specific company's business model:

```
subjectKind: cluster | account | case | theme | rule
signalType:  churn_risk | expansion | friction | kb_gap | automation_drift | outage | advocacy
```

Those are good values. They are also _someone's domain_, sitting in a schema that other teams are
supposed to adopt. A security team has no `churn_risk`; a finance team has no `kb_gap`. A catalog
that ships those enums is a catalog only one customer can use, and we would rather have one catalog
that serves everyone than five that each serve one.

So the rule now (contract principle 9): **no catalog ships an enum that names someone's business.**
Domain vocabulary travels as _data_. UI semantics — `intent`, `trend`, `align` — stay as enums,
because those are genuinely closed and genuinely universal.

### What changes on InsightCard

**`subjectKind` and `signalType` become free strings.** Strictly more permissive — every value you
emit today keeps working, and you can now emit `"vendor"` or `"policy_drift"` without a contract
change. **Zero edits on your side.**

**Four props collapse into two general ones.** This is the one real edit:

```jsonc
// 0.6.0
{
  "caseCount": 412,
  "revenueAtRisk": 48200,
  "currency": "USD",
  "themes": [{ "label": "Invoice errors", "count": 88 }]
}

// 0.7.0
{
  "metrics": [
    { "label": "Cases", "value": 412 },
    { "label": "Revenue at risk", "value": 48200, "unit": "USD", "intent": "bad" }
  ],
  "tags": [{ "label": "Invoice errors", "count": 88 }]
}
```

`themes` → `tags` is a rename; the item shape is unchanged. `metrics` is an array of
`{label, value, unit?, intent?}` — `unit` takes an ISO 4217 code for money, matching what
`ops` `Stat` already does, so the two catalogs finally format currency the same way.

You lose nothing: `metrics` renders the same stat row, and it takes as many figures as you want
rather than exactly the two we happened to guess. Each metric can now carry its own `intent`, which
`revenueAtRisk` never could.

### Ids

`insight` is a **new catalog id**: `.../catalogs/insight/v1.json`. The old
`.../catalogs/intel/v1.json` is frozen and **served forever** — nothing you have deployed stops
resolving. `@aurilabs/intel` stays on npm at 0.6.0 and keeps working; it just stops gaining
features.

### What you need to do

1. Pull the new prompt-pack section for InsightCard (the emission rules changed with the props).
2. Map `caseCount`/`revenueAtRisk`/`currency` → `metrics`, `themes` → `tags` wherever your agent
   emits InsightCard.
3. Swap the catalog id and the package name.

We will re-run the full emission gate across two model families on the new pack before it ships, so
you are not the ones discovering whether models can emit `metrics` cleanly.

## Why we are doing this now rather than later

Because you are the first consumer, and the cost of this migration will never be lower than it is
today. Every additional team that adopts `intel` makes the domain-specific enums more expensive to
remove — and they have to come out, because a catalog library whose components look like they were
built for one customer is not a library anyone else adopts.

If the `metrics` collapse is genuinely worse for your surface, say so before this lands. The
generality principle is not negotiable; this specific shape is.
