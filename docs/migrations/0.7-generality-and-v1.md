## 1. v1.0 conformance — and the two shapes that weren't ours to keep

Our contracts predate the final v1.0 catalog schema rules. Most of the work is invisible: helpers
inlined (rule 2), the `allOf` + `ComponentCommon` wrapper dropped because the envelope composes it
(rule 5), protocol primitives `$ref`'d to the spec's own `common_types.json` (rule 3), only legal
root keys kept (rule 7). None of that touches a component property.

But two of the types we `$ref`'d as "protocol primitives" turned out not to be the spec's types at
all. They are **svelte-a2ui extensions** — the renderer accepts them, the specification does not:

### `wantResponse` / `responsePath` are gone from actions

The spec's `Action.event` accepts exactly `name`, `userMessage` and `context`, and is
`additionalProperties: false`. It has never had `wantResponse` or `responsePath`.

```jsonc
// 0.6.0 — rejected by a conformant validator
{"event": {"name": "report_filed", "context": {...}, "wantResponse": true, "responsePath": "/err"}}

// 0.7.0
{"event": {"name": "report_filed", "context": {...}}}
```

**What replaces it:** reply with `updateDataModel` on the path you want written. You authored the
surface, so you already know the path — bind a `Callout` or a field's error to it when you build the
form. The only thing genuinely lost is the renderer-minted correlation id; if you need one, put it
in `context`.

**What you gain:** `event.userMessage`, the spec's human-readable description of what the user did,
for conversation history and feedback.

### Checks now carry their call inside `condition`

The spec's `CheckRule` is `{condition, message}` where `condition` is a `FunctionCall`. Ours was
flat. The renderer bridges both — which is exactly why this went unnoticed.

```jsonc
// 0.6.0
{"call": "length", "args": {"min": 30}, "message": "A sentence or two more helps."}

// 0.7.0
{"condition": {"call": "length", "args": {"min": 30}}, "message": "A sentence or two more helps."}
```

We keep the closed enum of five built-ins and keep `message` required, so ours stays a deliberate
_narrowing_ of the spec's type rather than a copy of it — a catalog is allowed to accept less than
the protocol, just not something different.

### Also widened: `dynamicValue`

Ours omitted `boolean`, `array` and plain objects. It now matches the spec's full union — strictly
more permissive, so nothing you emit today stops working.

### New ids

`ops` and `forms` move to **`.../catalogs/ops/v2.json`** and **`.../catalogs/forms/v2.json`**. The
v1 documents are frozen byte-exact in `contract/frozen/` and **served forever** at their original
urls; `@aurilabs/ops@0.6.0` and `@aurilabs/forms@0.6.0` stay on npm and keep working.

## 2. `intel` becomes `insight`, and stops naming anyone's business

`intel` ships two enums that encode a specific company's business model:

```
subjectKind: cluster | account | case | theme | rule
signalType:  churn_risk | expansion | friction | kb_gap | automation_drift | outage | advocacy
```

Those are good values, and they are _someone's domain_ sitting in a vocabulary other teams are meant
to adopt. A security team has no `churn_risk`; a finance team has no `kb_gap`. The rule now (contract
principle 9): **no catalog ships an enum that names someone's business.** Domain vocabulary travels
as data. UI semantics — `intent`, `trend`, `align` — stay closed enums, because those are genuinely
universal.

**`subjectKind` and `signalType` become free strings.** Every value you emit today keeps working,
and you can add your own without a contract change. Zero edits.

**Four props collapse into two:**

```jsonc
// 0.6.0
{"caseCount": 412, "revenueAtRisk": 48200, "currency": "USD",
 "themes": [{"label": "Invoice errors", "count": 88}]}

// 0.7.0
{"metrics": [{"label": "Cases", "value": 412},
             {"label": "Revenue at risk", "value": 48200, "unit": "USD", "intent": "bad"}],
 "tags": [{"label": "Invoice errors", "count": 88}]}
```

**Path bindings work inside `metrics[]`.** `resolveDynamic` recurses member-wise into arrays and
objects, so `{"label": "Cases", "value": {"path": "/ra/caseCount"}}` resolves like any top-level
binding. A metric whose binding has not resolved yet keeps its label and shows a placeholder rather
than disappearing from the row — the first consumer read the source to confirm this was safe, which
told us the old behaviour (silently filtering it out) was the bug, not the documentation.

`themes` → `tags` is a rename with the same item shape. `metrics` takes `{label, value, unit?,
intent?}` — `unit` is an ISO 4217 code for money, matching what `ops` `Stat` already does. It holds
as many figures as you want rather than the two we guessed, and each carries its own intent, which
`revenueAtRisk` never could.

`intel` takes its v1.0 conformance and its de-domaining **in one move**, as the new catalog
`.../catalogs/insight/v1.json` — one migration rather than two. `.../catalogs/intel/v1.json` is
frozen and served forever, from inside the `insight` package: the docs site serves every document at
the url in its **own** `catalogId`, so renaming the package could not move it.

The package is **`@aurilabs/insight`**. `@aurilabs/intel@0.6.0` stays on npm and keeps working; it
is superseded, not unpublished.

One implementation detail worth naming, because it was worse than the schema problem: the component
formatted `signalType` through a seven-entry label map and returned **nothing** for an unlisted
value. An agent emitting a perfectly valid `policy_drift` silently lost it. Domain strings are now
humanized generically (`policy_drift` → "policy drift"), and a browser test asserts that a word the
catalog has never seen still reaches the screen. Principle 9 applies to implementations, not just
schemas.

## 3. What you actually have to do

1. Drop `wantResponse`/`responsePath` from actions; reply with `updateDataModel` instead.
2. Wrap check calls in `condition` (forms).
3. Map `caseCount`/`revenueAtRisk`/`currency` → `metrics`, `themes` → `tags` (intel/insight).
4. Swap the catalog ids and pull the new prompt-pack sections.

We re-run the full emission gate across two model families on the new packs before shipping, so you
are not the ones discovering whether models emit these cleanly.

## Why now rather than later

Because a library that claims A2UI conformance has to actually have it, and because every additional
team that adopts these shapes makes them more expensive to correct. The extensions were load-bearing
in exactly one place each, and a React or Flutter port would have had to reimplement both to render
our catalogs — which is the clearest possible sign they did not belong in the vocabulary.

We're taking the gap upstream too: the server-side-verdict use case behind `responsePath` is real,
and a spec that has `actionResponse` on the wire but no way for a catalog to request one looks like
an oversight worth reporting.
